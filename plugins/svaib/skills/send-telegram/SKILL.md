# Send Telegram

Канал доставки в Telegram (Bot API). Отправляет сообщение получателю, настроенному в `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). Общий ресурс: другие скиллы делегируют доставку **агенту** — «отправить через скилл send-telegram», — а транспорт выбирается правилом ниже. При делегировании передай исполнителю окончательный текст, адресатов, выбранный режим и применимые требования оформления из основной инструкции и спецификации результата: родительский контекст может быть ему недоступен. Прямой запуск скриптов — путь для контуров, где агента нет.

## Сначала — чем слать

❗️ **Есть MCP-сервер `svaib` — отправляй его инструментом `send_telegram_message`, скрипты этого скилла не нужны.** Проверяется наличием инструмента в сессии; гадать не надо, он либо есть, либо нет. В вызове явно передавай выбранный режим в `mode` (`rich` или `plain`), не полагайся на умолчание инструмента.

Почему приоритет именно такой: доставка через шлюз попадает в журнал с исходом, получает ключ идемпотентности (повтор безопасен), ограничена правами твоего ключа и видна в аудите поимённо. Прямой путь этого не даёт ничего: ни журнала, ни защиты от дубля, ни ответа на вопрос «кто отправил».

**Адресатов спрашивай у шлюза — инструментом `list_contacts`.** Он возвращает доступные тебе чаты и личные адреса с назначением и состоянием бота; для отправки берёшь оттуда `alias` (или `binding_id`). Зови его перед отправкой всякий раз, когда получатель назван словами: перечень алиасов в схеме `send_telegram_message` кэшируется клиентом и устаревает, а `list_contacts` читается живьём. Локальный реестр `recipients.yaml` к этому маршруту отношения не имеет и не читается: два реестра адресатов, которые «почти совпадают», однажды разъедутся, и ценой будет сообщение, ушедшее не тому.

**Инструмента нет — работают скрипты ниже**, и они бьют в Bot API напрямую. Второго пути к шлюзу у скриптов нет намеренно: доставка через шлюз делается инструментом MCP, а «ещё один способ попасть туда же» пришлось бы объяснять каждый раз, когда неясно, чем ушло сообщение. Скрипты остаются для контуров, где шлюза не существует, — клиентские установки и аварийная процедура.

Пути к файлам скилла ниже — от его каталога: каталог сообщает среда. Скрипты запускай из корня пространства, указав полный путь до скрипта.

Что настроено на этой машине — покажет:

```bash
bash scripts/send_telegram.sh --check
```

Команда ничего не отправляет: печатает состояние кредов (факт наличия, не значения) и перечень известных адресатов.

Два скрипта в `scripts/` этого скилла:
- **`send_telegram.sh`** — plain (по умолчанию): markdown → HTML → `sendMessage` (parse_mode=HTML), нарезка по строкам ≤4096.
- **`send_telegram_rich.sh`** — rich (структурный): markdown → `sendRichMessage` (Bot API 10.1), при отказе API фолбэк на plain.

## The Iron Law

**Один шаг вместо двух вопросов.** Вопрос «показать превью или сразу отправить?» не задаётся никогда: покажи окончательный текст сообщения, если он ещё не показан, и одним вопросом уточни недостающее — получателя, если он не назван, или подтверждение, если назван не адресат по умолчанию. Ответ с адресатом — и есть подтверждение отправки. Получатель назван в запросе (или вызывающим скиллом), а окончательный текст уже показан — не показывай его повторно и не переспрашивай, отправляй.

Если вызывающий скилл требует явного подтверждения окончательного текста, дождись его перед отправкой; уже полученное подтверждение повторно не спрашивай.

**Плоский или rich.** Режим `rich` или `plain`, явно заданный пользователем или вызывающим скиллом, сохраняй. Только если режим не задан, выбирай по тексту: структурный вывод (таблицы, ≥2 секции, дайджест) → rich; короткое сообщение в 2-3 строки → plain. **Исключение при выборе по тексту:** если он уже свёрстан эмодзи-строками (`⭕️`/`✅`) вместо `-`, отправляй plain. В rich пункты списка обязаны начинаться с `-`, иначе строки схлопнутся в абзац (см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101)); нужные правки разметки готовь до показа, не меняя заданный режим.

## Кому отправляем

> **Сначала проверь, есть ли рядом со скиллом `scripts/recipients.py`.** Нет файла — реестра адресатов в этой поставке нет: доступен только адресат по умолчанию, `--to` не сработает, и всё ниже не применяется. Скажи об этом прямо, не пытайся обойти. Так же читай упоминание нескольких получателей в описании скилла: оно про возможность канала, а не про гарантию, что она включена здесь.

По умолчанию сообщение уходит в чат из `TELEGRAM_CHAT_ID`. Если пользователь **назвал получателя** — «отправь руководителю», «скинь в общий чат», «пошли обоим» — адресаты указываются по имени:

```bash
bash scripts/send_telegram.sh --to <алиас>[,<алиас>] "ТЕКСТ"
```

Имена (алиасы) живут в реестре `recipients.yaml`; посмотреть доступные — `python3 scripts/recipients.py --list`. Реестр хранит **имена ключей** окружения, а не номера чатов.

**Правила, которые нельзя нарушать:**

| Ситуация | Что делать |
|---|---|
| Пользователь назвал адресата, которого нет в реестре | Показать список известных и **спросить**. Не отправлять «пока себе», не подбирать похожего: ошибка адресации — это чужие глаза на содержимом, а не неудобство |
| Отправка не адресату по умолчанию | Рядом с показанным текстом назвать **кому именно** уходит сообщение и получить подтверждение. Не переспрашивать, если пользователь сам назвал получателя в запросе |
| Отправка в групповой чат | Помнить и при необходимости сказать вслух: сообщение увидят **все участники чата**. Поле `members` в реестре — справочное, реальный состав группы может быть шире |
| Часть адресатов не получила | Скрипт вернёт сводку по каждому. Передать её пользователю как есть — там различаются «не доставлено» и «исход неизвестен» |
| Исход неизвестен (код возврата 2) | **Не отправлять повторно** без проверки чата: сообщение могло дойти, и повтор его продублирует |

## Алгоритм

### 1. Получить текст

Текст сообщения — из аргументов (`$ARGUMENTS`) или из контекста разговора. Если неясно что отправлять — спроси.

Сообщение агента по поручению человека, в том числе в общий чат, заканчивается подписью «— svaib, по поручению {имя}»: например, «— svaib, по поручению Эрика». Подпись — отдельный абзац, целиком курсивом: в plain `__— svaib, по поручению {имя}__`, в rich `*— svaib, по поручению {имя}*` (`__…__` в rich даёт жирный). Имя поручившего бери из `map_profile` или `whoami`, а если поручение передано другим скиллом — из его контекста; это не имя получателя. Неизвестно, кто поручил, — уточни. Подпись добавь до показа текста, существующую подпись агента приведи к этому виду без дублирования. Автономное уведомление без поручителя подписывай тем же образом «— svaib».

До показа проверь оформление по разделу «Форматирование» и разметку под выбранный режим, в том числе после сокращений. Готовую rich-структуру сохраняй и при показе на согласование: заголовки, списки и таблицы остаются на месте. Если для выполнения требований нужна правка уже согласованного текста — содержания, подписи или разметки, — подготовь исправленную версию и получи её подтверждение до отправки. Переданное одобрение относится только к неизменному тексту и указанным адресатам.

### 2. Адаптировать формат под Telegram (только обычный режим)

Если выбран **rich-режим**, этот шаг пропусти: подготовленный markdown передаётся rich-транспорту как есть (см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101)).

В plain до показа и согласования приведи текст к формату, который Telegram отобразит корректно:
- `## заголовок` / `### заголовок` → `**заголовок**` (plain не поддерживает заголовки; имеющиеся знаки и текст сохраняются)
- `- [x] текст` → `- ✅ текст` (скрипт убирает только `[ ]`, не `[x]`)
- `---` → убрать (скрипт убирает, но лучше не полагаться)

### 3. Показать текст и уточнить получателя

Покажи окончательный текст сообщения, если он ещё не показан: вызывающий скилл мог уже показать и согласовать эту версию с теми же адресатами. В таком случае повторные показ и подтверждение не нужны. Получатель не назван — спроси одним вопросом: «Кому отправить?». Дальше действуй по The Iron Law; если согласованный текст пришлось изменить, покажи исправленную версию и дождись её подтверждения. В отправку передавай именно окончательный текст, без последующих правок подписи, содержания или разметки.

### 4. Отправить (обычный режим)

```bash
bash scripts/send_telegram.sh "ТЕКСТ_СООБЩЕНИЯ"
```

Проверить: ответ содержит `"ok":true`. Скрипт возвращает **ненулевой exit** при недоставке любого чанка. (Rich-режим отправляется скриптом `scripts/send_telegram_rich.sh` — см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101).)

### 5. Подтвердить

Сообщить результат:
- Успех: «Отправлено в Telegram»
- Ошибка: показать ответ API

Вызывающему скиллу вместе с исходом доставки верни окончательный текст, переданный в транспорт, чтобы он сохранил именно эту версию.

## Edge Cases

| Ситуация | Действие |
|----------|----------|
| `.env` не найден | Оба скрипта ищут `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` одинаково: env → `./.env` → git-root/.env. Уже заданная переменная окружения побеждает файл — покаждой отдельно, включая `TG_CHAT_*`. Если нигде нет — сообщить: «.env с TELEGRAM_BOT_TOKEN не найден» |
| Текст >4096 символов (plain) | Скрипт режет по строкам (теги не рвутся) — предупредить: «Длинное сообщение, уйдёт частями». MCP-инструмент шлюза `send_telegram_message` в plain-режиме не режет, а отвергает (`body-too-large`) — дели текст сам. Rich — до 32768, без деления |
| Rich: лимиты sendRichMessage | До 32768 символов, 500 блоков, 16 уровней вложенности, 50 медиа, 20 колонок таблицы. Больше — разбей на несколько сообщений по секциям |
| curl вернул ошибку | Скрипт вернёт ненулевой exit. Если 403 — напомнить про Allow network egress (Cowork) |
| Пустой текст | Скрипт вернёт ошибку. Спросить что отправлять |
| Реестр адресатов не найден | `--to` недоступен. Сказать: «реестра адресатов нет, могу отправить только в чат по умолчанию» |
| Неизвестный алиас в `--to` | Ни одному адресату **ничего не ушло** — список разрешается целиком и до отправки. Показать известные и спросить |
| Ключ `TG_CHAT_*` не задан в окружении | То же: не отправлено никому. Назвать недостающий ключ, не подставлять другой |
| Реестр от чужого бота | Отказ до отправки: `chat_id` зависит от пары «бот + получатель», у другого бота те же номера означают другие чаты |
| «bot is not a member» / «not enough rights» | Бота нет в группе или у него нет права писать. Добавить бота в чат; для группы у @BotFather может понадобиться `/setprivacy → Disable` |
| Частичный отказ (код 1) | Кому доставили — доставили, откатить в Telegram нельзя. Показать сводку; повторять только тем, у кого ❌ |
| Исход неизвестен (код 2) | Проверить чат глазами до любого повтора |

## Пример

**Запрос:** «Скинь в тг список задач на завтра»
1. Скилл выполняет подготовку по шагам 1–2 и показывает готовый текст с подписью.
2. Получатель не назван → «Кому отправить?».
3. Пользователь: «мне» → отправить этот же подготовленный текст выбранным транспортом в выбранном режиме.
4. Ответ API `"ok":true` → «Отправлено в Telegram».

**Запрос:** «отправь <имя получателя>: Встреча перенесена на 15:00»
1. Скилл выполняет подготовку по шагам 1–2, включая подпись; недостающее имя поручителя уточняет до показа.
2. Показывает окончательный текст и названного получателя; дополнительного вопроса об отправке не нужно.
3. Отправляет этот же подготовленный текст выбранным транспортом в выбранном режиме и сообщает исход.

## Форматирование

Оформление задают основная инструкция агента и применимая спецификация результата с учётом правил пространства и личных настроек в их действующем приоритете. Сохраняй заданную ими структуру и вид; если готовый текст уже согласован, действуй по шагу 3. Здесь — только технические особенности Telegram.

**Переносы зависят от режима.** В plain одиночный перенос сохраняет новую строку, пустая строка разделяет абзацы. В rich пустая строка разделяет markdown-блоки, а перенос внутри абзаца задаётся обратным слэшем `\` в конце строки.

### Plain-режим: возможности конвертера

Оба маршрута преобразуют разметку в HTML для `sendMessage` (`parse_mode=HTML`):

| Приём | Что писать | Результат |
|-------|-----------|-----------|
| Жирный | `**текст**` | `<b>текст</b>` |
| Курсив | `__текст__` | `<i>текст</i>` |
| Зачёркивание | `~~текст~~` | `<s>текст</s>` |
| Ссылка на словах | `[текст](url)` | `<a href="url">текст</a>` |
| Custom emoji | `![📌](tg://emoji?id=N)` | `<tg-emoji emoji-id="N">📌</tg-emoji>` |
| Обычные эмодзи и списки | `📌`, `- Пункт` | Как есть |
| Пустой чекбокс | `- [ ] Пункт` | `- Пункт` |
| Разделитель | `---` отдельной строкой | Пустая строка |

Сырые HTML-теги экранируются и видны как текст. Таблицы, картинки, код и markdown-заголовки конвертер не оформляет. Разметка действует внутри одной строки. У жирного внутри не может быть `*`, у курсива — `_`, у зачёркивания — `~`; пересекающиеся маркеры дают невалидные теги. Правильная вложенность поддерживается, например `~~**текст**~~`.

Ссылка — непустая подпись без квадратных скобок и адрес без пробелов, с парными круглыми скобками. Markdown-заголовки ссылок (`[текст](url "title")`) и вложенные ссылки не поддерживаются. Маркеры внутри адреса сохраняются, атрибуты HTML экранируются. У custom emoji `N` — строка из цифр ASCII; это ID emoji, не ID стикерпака. Неподдерживаемые картинки остаются текстом.

**Custom emoji требуют права бота.** Поддержка тега конвертером не гарантирует показ в конкретном чате. По Bot API вариант с Premium владельца действует для private/group/supergroup; для канала нужно отдельно подтвердить право целевого бота и результат отправки. Успех rich этого не доказывает. При отказе сообщи его, не объявляй замену обычным emoji выполнением запроса на custom emoji.

## Rich-режим (sendRichMessage, Bot API 10.1)

Для **структурного** вывода — отдельный скрипт. Бот шлёт document-grade сообщение прямо в чат. Контент — GFM-подобный markdown.

**Когда:** выбран `rich` по правилу «Плоский или rich» выше. Явно заданный rich сохраняется и для короткого сообщения.

**Как:**

```bash
bash scripts/send_telegram_rich.sh "MARKDOWN"
```

Проверить ответ `"ok":true`. **Фолбэк** срабатывает только при **подтверждённом отказе API** (`ok:false`) — тогда скрипт шлёт обычным `send_telegram.sh`, и только тому адресату, у которого rich не прошёл: остальные уже получили своё, повторный веер продублировал бы им доставку. При сетевом timeout фолбэка НЕТ (исход неизвестен — чтобы не словить двойную доставку), скрипт вернёт ошибку. И фолбэк **теряет rich-форматирование**: таблицы / `<details>` / код уйдут сырой разметкой — это аварийная доставка текста, не замена rich.

> ⚠️ **В rich имена файлов и пути — в inline-code.** Telegram может распознать `cowork.md` или `product/03_backlog.md` как адрес и сделать нерабочую ссылку. Оборачивай их в обратные кавычки. Plain-конвертер inline-code не поддерживает.

### Палитра элементов и статус проверок

В таблице — синтаксис rich Markdown. Пометки «проверено 06.10» относятся к конкретным прошлым проверкам в клиенте Telegram. Пустая строка разделяет markdown-блоки; фиксированный визуальный зазор не обещаем. Новый компактный пример в клиенте Telegram не проверен (статус на 2026-10-13).

| Элемент | Синтаксис | Примечание |
|---|---|---|
| Заголовок | `## Текст` (число `#` → size 1–6) | |
| Разделитель | `---` | видимая линия между смысловыми секциями, если нужна; пустая строка до и после |
| Отдельный абзац | одна пустая строка в исходном markdown | разделяет блоки; визуальные отступы задаёт Telegram |
| Перенос внутри абзаца | `\` в конце строки | строки стоят подряд без зазора; два пробела в конце тоже работают, но теряются при правке; `<br>` не подтверждён (проверено 06.10) |
| Таблица | GFM (пайпы + строка-разделитель) | |
| Код | fenced-блок с языком | подсветка синтаксиса |
| Чек-лист | `- [x]` / `- [ ]` | рендерит галочки |
| Сворачивающийся блок | `<details><summary>…</summary>…</details>` | raw-HTML внутри markdown работает |
| Формула | `$…$`, вкл. `\sqrt{}`, `\cdot` | |
| Картинка | `![alt](URL)` | нужен публичный URL — см. ниже |
| Цитата | `> текст` | |

**Картинки — URL, доступный серверам Telegram по HTTP/HTTPS.** Telegram сам выкачивает картинку по ссылке (на практике кэширует к себе); локальный файл в markdown не вставить. Бери готовый публичный URL; если картинку нужно сначала где-то разместить — согласуй с пользователем, куда её выложить (запрос «отправь в телеграм» сам по себе прав на публикацию файлов не даёт).

### Три правила rich-разметки

1. **Без искусственных пустых блоков.** Абзацы разделяй одной пустой строкой в исходном markdown. Не вставляй отдельные абзацы из U+2800 (braille blank) или U+00A0 для зазоров: они не задают надёжный размер отступа. Заголовок уже отделяет секцию; `---` нужен только для видимой линии, с пустой строкой до и после. Без пустой строки перед `---` предыдущий абзац становится setext-заголовком.
2. **Списки: вложение только «хвостом».** Плоские списки — ок. Вложенные буллеты — только под **последним** пунктом. Нельзя продолжать нумерацию после вложенного блока: «2 → вложенные → 3» ломает рендер (пункт 3 съезжает под вложение). Правильно: «1, 2, 3 → вложенные под 3».
3. **Одиночный перенос склеивает строки в абзац (мягкий разрыв GFM).** Строки без маркера (`⭕️ …`, голый текст) схлопываются в один `paragraph`. Пункты списка — только через `-`; проверяй по `rich_message.blocks` в ответе API: каждый пункт — отдельный блок, а не склейка. Строки, которые должны стоять подряд без маркера (пара реплик «Я / svaib»), — `\` в конце строки.

**Рендер зависит от клиента-получателя:** телефон — чисто, десктоп пока сыровато (фича от июня 2026). Фолбэк тут НЕ помогает — он только на ошибку API, а не на плохой рендер при `ok:true`.

## Скрипты

Оба принимают `[--to alias[,alias...]] [--] "ТЕКСТ"`. Без `--to` поведение прежнее и реестр не нужен. `--` завершает флаги — нужен, если текст начинается с дефиса.

Коды возврата различают **исход доставки** и **отказ до неё**:

| Код | Что случилось | Что делать |
|---|---|---|
| `0` | Доставлено всем | — |
| `1` | Подтверждённый отказ: Telegram разобрал запрос и отверг | Повтор безопасен — сообщение точно не дошло |
| `2` | **Исход неизвестен**: обрыв, 5xx, неразборный ответ | **Не повторять.** Сначала посмотреть чат: сообщение могло дойти |
| `3` | Не отправлено никому: ошибка вызова или предусловия | Починить конфигурацию и запустить заново |

Двойка важнее единицы: если у одного адресата отказ, а у другого неизвестность — вернётся `2`.

- **Реестр адресатов**: [scripts/recipients.py](scripts/recipients.py) — `--resolve` (алиасы → имена ключей), `--list`, `--validate [--strict]`. Значений chat_id не хранит и не печатает: их подставляет shell, у которого резолв `.env` уже есть.
- **Общая часть**: [scripts/_channel_common.sh](scripts/_channel_common.sh) — разбор аргументов, креды, разрешение адресатов. Подключается обоими скриптами, чтобы логика снова не разошлась.
- **Обычный** (по умолчанию): [scripts/send_telegram.sh](scripts/send_telegram.sh) — резолвит `.env` (env → pwd → git-root) → экранирует HTML → конвертирует разметку по таблице plain → `sendMessage` (parse_mode=HTML) → режет по строкам ≤4096 → проверяет `ok` (ненулевой exit при недоставке). Конвертация и нарезка выполняются один раз на всех адресатов.
- **Rich** (структурный): [scripts/send_telegram_rich.sh](scripts/send_telegram_rich.sh) — резолвит креды тем же правилом, что обычный (env → pwd → git-root; в кластере креды приходят переменными, файла там нет) → markdown → `sendRichMessage` (Bot API 10.1) → фолбэк на обычный **только при подтверждённом отказе**: ответ 4xx. Ответ 5xx, неразборное тело при 200 и сетевой обрыв фолбэка не дают — исход неизвестен, и вторая отправка продублировала бы уже принятое сообщение.
